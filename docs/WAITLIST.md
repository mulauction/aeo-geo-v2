# WAITLIST (MVP) — 수집 구조 확정 문서

본 문서는 **MVP 단계의 PRO 대기자(Waitlist) 수집 구조를 문서로 확정**하기 위한 기준입니다.  
**코드/서버/UI 구현은 포함하지 않으며**, Phase A-2에서 구현합니다.

---

## 목적 / 범위 (MVP 기준)

- **목적**: PRO 기능에 관심 있는 사용자의 연락처(이메일) 수집 → 출시/베타/우선순위 안내
- **범위**: Share 화면의 “대기자 등록” CTA를 통해 새 탭에서 외부 수집 폼으로 유입
- **비범위**:
  - 결제/구독/요금제 활성화
  - 잔여/쿼터 차감, 로그인 강제, 서버 스냅샷/리포트 로직
  - 사용자 식별을 위한 추가 개인정보(이름/전화번호 등)

---

## 수집 항목 (최소 수집)

- **필수**: 이메일(email) 1개
- **옵션 필드**: MVP에서는 **배제**
  - 예: 회사명/브랜드명/상품 URL/연락처/직군/월 사용량/메모 등

---

## 수집 방식 후보 비교

| 후보 | 개요 | 장점 | 단점/리스크 | 운영 난이도 |
|---|---|---|---|---|
| 외부 폼 (Tally / Google Form 등) | 폼 서비스로 이메일 수집, CSV/시트로 관리 | 구현/배포 빠름, 보안/스팸 필터 기본 제공(서비스 의존) | 데이터가 외부에 존재, 커스텀 로직 제한, 도메인/브랜딩 제약 | 낮음 |
| 자체 서버 endpoint | `/waitlist` 같은 API로 직접 저장/중복 처리 | 완전한 통제(중복/분석/세그먼트), 추후 확장 용이 | 개발/운영 부담, 보안/스팸 방어 직접 구현 필요, 법/정책 대응 책임 증가 | 중~높음 |

---

## MVP 최종 선택 (결정)

### 선택: **외부 폼(예: Tally/Google Form)**

- **이유**
  - MVP에서 가장 중요한 것은 “관심 사용자 확보”이며, **수집 인프라를 최소 비용/최단 시간**으로 마련하는 것이 우선
  - 서버/DB/인증/보안/스팸 방어/운영 모니터링 등 **추가 표면적을 만들지 않음**
  - Share는 새 탭 이동 기반이므로, 외부 폼 UX와 잘 맞음

---

## 중복 처리 정책 (동일 이메일 재등록)

- **정책**: 동일 이메일로 재등록 가능 (사용자 관점에서 “등록됨”을 확신할 수 있도록 허용)
- **운영 처리**:
  - 외부 폼/시트에서 **중복 이메일은 최신 등록 시각으로 갱신**하거나
  - 내부 운영 시 “dedupe view(최신 1개)”를 별도 관리
- **사용자 메시지**: “이미 등록하신 이메일이라도 다시 제출할 수 있습니다” 정도의 짧은 안내(Phase A-2 이후 UI에서 검토)

---

## 보관 기간 / 삭제 요청 처리

- **보관 기간(권장)**: 목적 달성 후(베타/출시 안내 종료) 또는 **최대 12개월** 내 정리
- **삭제 요청 처리**
  - 이메일을 기준으로 삭제 가능해야 함
  - 삭제 요청 채널은 “회신 이메일” 또는 별도 문의 채널로 처리(운영 정책)
  - 삭제 완료 후 재등록은 가능(사용자 의사 존중)

---

## 스팸 / 보안 최소 방어 (MVP)

- **필수 방어**
  - 외부 폼 제공 기능 활용: reCAPTCHA/봇 방지/레이트 리밋(가능한 범위)
  - 공개 공유 링크에 직접 이메일 노출/로그 출력 금지
- **운영 가드레일**
  - 수집 데이터 접근 권한 최소화(필요 인원만)
  - 내보내기 파일(CSV 등) 보관/공유 최소화

---

## Phase A-2 구현 체크리스트 (아직 구현하지 않음)

- **링크/트래킹**
  - Share의 “대기자 등록” 클릭 시 외부 폼 새 탭 열기
  - UTM(또는 유사) 파라미터로 유입 경로 기록
- **필드**
  - 이메일 1개만 필수로 받기(옵션 필드 추가 금지)
- **중복/운영**
  - 동일 이메일 중복 처리(최신 갱신 또는 dedupe view)
  - 보관 기간/삭제 요청 플로우 내부 운영 문서화
- **품질**
  - 스팸 방어 옵션(캡차/레이트 리밋) 활성화
  - 접근 권한 최소화
